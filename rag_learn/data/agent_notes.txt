智能体为什么必须外挂工具

大语言模型的本质是逐词预测，它没有循环、没有变量、没有中间状态，所以做不了精确的多步计算。这不是训练不够，而是结构决定的。既然模型本体算不准，工程上的办法就是让它学会"调用外面算得准的程序"，这就是 Function Calling 存在的理由。模型负责判断该调用哪个工具、参数填什么，真正的执行交给确定性的代码。

工具调用的完整循环

一次工具调用包含四步：把工具的 JSON Schema 一起发给模型，模型返回一个 tool_calls 结构，程序解析出工具名和参数并真正执行，最后把执行结果作为一条 tool 角色的消息回传给模型，让它继续下一步。这个循环要写成 while 循环而不是一次 if，因为模型可能需要先查天气再算车费，第二步依赖第一步的结果。官方示例里常见的 tool_calls[0] 写法会丢掉同一轮里的多个工具调用，正确做法是遍历整个列表。

流式返回下的工具调用

开启流式之后，工具调用不再是完整的一块，而是被切成很多碎片陆续推来，第一块带 id 和函数名，后面的块只带被切碎的参数字符串。所以必须按碎片里的 index 累积拼接，才能还原出完整的 arguments。这件事必须处理，否则流式和非流式会需要两套工具执行代码，而把碎片拼成和非流式完全相同的形状之后，执行工具的函数就能两边通用。

arguments 是字符串不是字典

模型返回的 arguments 是一个 JSON 格式的字符串，而不是 JSON 对象，根因在于语言模型只会输出文字，结构化数据只是碰巧长得像 JSON 的文字。程序必须自己做 json.loads 才能拿到字典。而且能解析成功并不意味着内容合规，它可能是空值、类型不对、多出字段，或者整个内容是模型编的。所以参数校验必须单独做一层。

模型给的东西不可信

工具的入参来自模型，而模型可能被提示词注入影响，所以直接把 arguments 交给 eval 执行等于让模型在你机器上跑任意代码。可行的解法是用 ast 把表达式解析成语法树，只放行数字和四则运算符。推而广之，凡是模型产出、用户输入、检索结果这类外部内容，进入执行路径之前都必须经过白名单校验。

稳定信息不要依赖检索

实测中发现语义检索捞不准：用户问天气时，库里"我在杭州工作"这条真正有用的信息只排第四名，top_k 取三就会漏掉。原因是语义相似度和实际有用性是两个不同的东西。所以真实 Agent 的做法是把名字、城市这类稳定信息固定写在系统提示词里，检索只负责捞那些不确定会用到的大段资料。系统提示词也不是一次性写死的，每一轮都要根据用户档案、当前时间、可用工具重新拼装。
